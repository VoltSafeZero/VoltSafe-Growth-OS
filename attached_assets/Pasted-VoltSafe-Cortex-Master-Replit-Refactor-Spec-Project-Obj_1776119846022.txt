VoltSafe Cortex — Master Replit Refactor Spec

Project Objective

Refactor VoltSafe Cortex into a cleaner CMS/CRM architecture without breaking existing data, fields, records, integrations, or working functionality.

This refactor must:
	•	unify external relationship management under a single CRM structure
	•	remove architectural duplication between CRM and Industry Partnerships
	•	preserve all existing production data and workflows
	•	support safe phased migration, validation, and rollback
	•	improve long-term scalability for sales, partnerships, deployments, subscriptions, and support

⸻

VoltSafe Cortex should behave like this:

3) Non-Destructive Refactor Rules

This refactor must be implemented as a non-destructive, backward-compatible migration.

The system must not:
	•	delete existing tables
	•	delete existing columns
	•	rename existing columns in place if current code depends on them
	•	remove existing routes or APIs that current UI depends on
	•	break current forms, record creation flows, search, filters, or record editing
	•	break current CRM records
	•	break current Industry Partnerships records before migration is verified
	•	break current email integration
	•	break user permissions
	•	break linked notes, files, comments, attachments, or activity history
	•	overwrite production data without backup and rollback capability

Implementation principle

Use additive refactoring first, then controlled migration, then validation, then soft deprecation.

⸻

4) Required Development Approach

Implement using this sequence:

Step 1 — Audit the existing system first

Before changing anything, inspect and document:
	•	current database schema
	•	all existing tables
	•	all columns and relationships
	•	current forms
	•	current APIs
	•	current UI pages and components
	•	existing filters and search
	•	current email linking logic
	•	existing automations
	•	existing permissions
	•	attachments and notes structure

Step 2 — Preserve compatibility
	•	keep existing tables and fields operational while new structures are introduced
	•	add new tables/columns instead of replacing old ones immediately
	•	use compatibility adapters, mapping layers, or translation services where needed
	•	maintain current working UI behavior until replacement views are complete and tested

Step 3 — Migrate safely
	•	migrate data into new structures with explicit scripts
	•	do not delete old structures during first migration
	•	mark old structures as legacy only after validation
	•	support rollback if migration output is incorrect

Step 4 — Switch over gradually
	•	update backend and UI in phases
	•	use feature flags where practical
	•	validate record counts, field mappings, and workflows before cutover
	•	only deprecate legacy code after QA and manual signoff

5) Preferred Canonical Company Object Strategy

Before creating a brand new organizations master table, first inspect whether the existing Accounts table can serve as the canonical company object.

Preferred approach
	1.	inspect existing Accounts structure
	2.	if viable, evolve Accounts into Organizations
	3.	reuse existing IDs and relationships wherever possible
	4.	migrate Industry Partnerships data into the same company master structure
	5.	expose Organizations as the UI label for Accounts if practical

Avoid this unless absolutely necessary

Do not create two competing company masters such as:
	•	Accounts
	•	Organizations

That causes duplication, broken references, and long-term data rot.

If existing Accounts can be extended safely, use that path.

	2.	create or extend the canonical Organizations model
	3.	migrate Industry Partnerships records into Organizations

	5.	preserve original source module in a legacy source field
	6.	map old category structure into:
	•	organization_type_primary
	•	relationship_role
	•	lifecycle_stage
	•	tags / saved views
	7.	preserve all notes, contacts, files, timestamps, and owners
	8.	compare migrated row counts vs original row counts
	9.	compare random sample records for correctness
	10.	only hide old Industry Partnerships UI after validation

Legacy mapping example
	•	Industry & Associations → Association / Industry Group
	•	Govt & Public Sector → Government Agency or Port / Harbor Authority
	•	Channel Partners → Distributor / Reseller or Strategic Partner
	•	Manufacturing → Manufacturer / Contract Manufacturer
	•	Innovation & Research → Research Institution
	•	Media & Tradeshows → Media / Press
	•	Other → Other

The existing CRM module must remain functional during migration.

Do not:
	•	re-key accounts, contacts, opportunities, or quotes in a way that breaks references

27) Email Auto-Linking System

Build an email ingestion and linking pipeline.

Step 1 — Parse email metadata

Capture:
	•	message_id
	•	thread_id
	•	subject
	•	from_address
	•	to_addresses
	•	cc_addresses
	•	bcc_addresses
	•	sent_at
	•	body_text
	•	body_html
	•	attachments
	•	in_reply_to
	•	references

Step 2 — Match sender to Contact

Priority:
	1.	exact email match to contacts.email_primary
	2.	exact email match to contacts.email_secondary
	3.	known alias mapping
	4.	shared inbox handling rules

Step 3 — Match domain to Organization
	•	extract sender domain
	•	check domains table
	•	if matched, attach organization
	•	if personal email, try existing manual mapping from contact to organization
	•	if multiple matches, reduce confidence and send to review

Step 4 — Match to Opportunity

Priority:
	1.	existing thread previously linked to opportunity
	2.	quote number in subject/body
	3.	contract number in subject/body
	4.	direct reply to Cortex-generated email tied to opportunity
	5.	single open opportunity under matched organization
	6.	multiple open opportunities = review path

Step 5 — Match to Quote / Deployment / Ticket if applicable
	•	quote number in subject/body → attach quote
	•	deployment site name/code → attach deployment
	•	ticket id/support pattern → attach ticket

Step 6 — Create Activity records

Create one activity row for matched entities:
	•	organization_id
	•	contact_id
	•	opportunity_id if found
	•	quote_id if found
	•	deployment_id if found
	•	ticket_id if found

Step 7 — Update summary fields

Update:
	•	contacts.last_activity_at
	•	organizations.last_activity_at
	•	opportunities.last_activity_at
	•	last_inbound_email_at / last_outbound_email_at

28) Email Confidence Scoring

High confidence
	•	exact contact email match
	•	exact organization domain match
	•	exact thread match
	•	exact quote/contract identifier match

Action:
	•	auto-link immediately

Medium confidence
	•	domain match only
	•	contact matched but multiple open opportunities
	•	weak subject keyword match

Action:
	•	auto-link and flag for review

Low confidence
	•	personal email with no known mapping
	•	multiple possible organizations
	•	multiple possible opportunities
	•	forwarded thread with mixed context

Action:
	•	send to email_link_reviews
	•	do not fully auto-link until approved

31) Email Safety Rules

Do not break existing email integrations or current email-linked records.

Requirements:
	•	preserve current email ingestion logic until new logic is tested
	•	do not detach historical associations
	•	preserve message IDs and thread IDs
	•	preserve activity history generated from email
	•	use new linking logic first for new messages or staged test mode
	•	if reprocessing historical email is needed, do it in a separate controlled backfill job

Recommended approach:
	•	keep current email tables and associations intact
	•	add new matching/enrichment logic on top
	•	avoid rewriting historical links unless clearly beneficial and fully auditable
