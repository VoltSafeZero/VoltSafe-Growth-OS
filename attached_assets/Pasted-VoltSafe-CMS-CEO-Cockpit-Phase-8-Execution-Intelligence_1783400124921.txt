VoltSafe CMS — CEO Cockpit Phase 8: Execution Intelligence, Drift Detection, and Commitments Radar

Goal:
Build an execution intelligence layer that detects operational drift before it becomes a fire.

The system should compare:
- what people committed to
- what tasks/actions were created
- what changed since the last briefing
- what is overdue, stale, blocked, or silently drifting
- what keeps recurring without resolution

This phase should make the CEO Cockpit proactive, not reactive.

Context:
Phase 4 built CEO Cockpit insights.
Phase 5 built 1:1 notes, agendas, and commitment extraction.
Phase 6 built the CEO Action Queue.
Phase 7 built Daily Briefing, Weekly Review, Team Briefings, and Leadership Agenda.

Now build Phase 8 as the “execution radar” layer on top.

Core requirements:

1. Execution Intelligence service
Create:

server/services/ceo-execution-intelligence.ts

Functions:

- buildExecutionRadar(actorUser, options)
  Returns a structured view of execution risk across team, tasks, commitments, action queue, opportunities, and blockers.

- detectExecutionDrift(actorUser, options)
  Detects items that are slipping, stalled, repeatedly snoozed, repeatedly dismissed, or aging without progress.

- buildCommitmentsRadar(actorUser, options)
  Tracks commitments from 1:1s, meeting notes, action queue, and tasks.

- buildRecurringRiskPatterns(actorUser, options)
  Finds repeat blockers, repeated overdue patterns, recurring stale opportunities, and unresolved themes.

- buildExecutionScorecard(actorUser, options)
  Produces simple operational metrics for CEO use.

No external API calls.
No OpenAI dependency required.
Use local DB only.
Do not auto-send anything.

3. Drift detection rules
Implement deterministic drift rules.

Examples:

Critical drift:
- critical/high action queue item overdue
- blocker open more than 7 days
- commitment due date missed
- important opportunity past expected close date
- task marked blocked with no update for more than 3 days

Slipping commitment:
- commitment accepted but no task created
- task created from commitment but still open after due date
- commitment appears in more than one 1:1 without completion

Repeated snooze:
- same action snoozed 2+ times
- snoozed high-priority action now due again

Stale task:
- active task with no update for 7+ days
- overdue task with no recent activity
- task assigned but never touched

Recurring risk:
- same owner has 3+ overdue items
- same source/project produces repeated blockers
- same opportunity appears stale across multiple weekly reviews
- same theme appears in multiple action queue items

Execution win:
- blocker resolved
- commitment completed
- overdue item closed
- high-priority action completed
- stale opportunity moved forward

Keep thresholds centralized in one object so they are easy to adjust.

5. Execution Scorecard
GET /api/today/ceo-execution/scorecard should return:

Metrics:
- open CEO actions
- overdue CEO actions
- completed this week
- dismissed this week
- snoozed active
- open blockers
- blockers resolved this week
- overdue commitments
- commitments completed this week
- stale tasks
- stale opportunities
- owner load distribution
- execution health score: 0–100

Health score should be simple and deterministic.
Do not pretend it is scientific.

Suggested scoring:
Start at 100.
Subtract:
- 8 for each critical drift item, max 32
- 5 for each overdue high-priority action, max 20
- 4 for each overdue commitment, max 20
- 3 for each unresolved blocker older than 7 days, max 15
- 2 for each stale task, max 10
- 1 for each repeated snooze, max 5

Clamp between 0 and 100.

Return:
- score
- label: Strong | Watch | At Risk | Critical
- reason
- contributing_factors

GET /api/today/ceo-execution/recurring-risks

POST /api/today/ceo-execution/items/:id/dismiss

Rules:
- create-action should use the Phase 6 CEO Action Queue service.
- dismiss should not delete source data.
- mark-reviewed should record review state only.
- no route may auto-send Currents or email.
- all routes require admin.
- preserve capital gating.
