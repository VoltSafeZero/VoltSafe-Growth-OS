Backend routes

Add authenticated routes under /api/current.

Add group DM members

POST /api/current/dms/:id/members

Body:

{
  "userIds": [123, 456]
}

Rules:

1. Requires authentication.
2. Current user must be a member of the group DM.
3. Conversation must be group_dm.
4. Reject use on 1:1 DMs.
5. Validate all users exist and are active/internal.
6. Exclude current members.
7. Reject if no new valid users remain.
8. Insert new rows into current_conversation_members.
9. Preserve existing members’ read/mute state.
10. Return updated conversation/member list.
11. Do not create duplicate member rows.
12. Enforce reasonable max group size, matching Phase 11A limit if one exists.
13. Notify newly added users if notification system supports it cleanly.

Leave group DM

POST /api/current/dms/:id/leave

Rules:

1. Requires authentication.
2. Current user must be a member.
3. Conversation must be group_dm.
4. Reject use on 1:1 DMs.
5. Remove or soft-archive the current user’s member row.

Preferred behavior:

* Soft leave if schema supports it, e.g. left_at.
* If no left_at exists, carefully delete the member row.

Consider adding columns if needed:

* left_at
* left_by

If adding left_at, update all membership checks to require left_at IS NULL.

6. User who left should no longer see the group DM in list.
7. User who left cannot read/send/mark-read/mute/upload attachments.
8. Existing messages remain visible to remaining members.
9. If only one member would remain, either:
    * allow it but group becomes effectively inactive, or
    * block leaving as last/second-last member.

Preferred: allow leaving unless it would leave zero members; document behavior.

Display/system message behavior

If low-risk, add system messages such as:

* Trevor added Alex to the conversation
* Sarah left the conversation

Only do this if existing message rendering can safely support system messages.

If not low-risk, skip system messages and just toast in UI.
