Investigation report accepted. Plan approved with the following adjustments and answers to your seven open questions.
Architectural adjustment
Delete the source=gmail | local | auto URL parameter entirely in this PR. Do not keep source=gmail and source=auto as "escape hatches" — leaving unreachable code paths is technical debt that won't get cleaned up later.
If there's a legitimate debugging scenario that requires querying live Gmail directly (bypassing the local DB), implement it as a separate explicit endpoint (e.g., POST /api/admin/gmail/probe for admins only). Don't leave dead branches on the main inbox endpoint.
If you have a specific reason to keep the escape hatch that I'm not seeing, articulate it before implementing — but the default is full removal.
Answers to open questions
1. Scope — apply unified-source treatment to all tabs that currently use mailSource. Inspect which tabs use it and report. If Sent and Drafts read from email_messages (which they likely do per the schema), they get the same treatment in this PR. If any tab reads from a fundamentally different source, flag it and I'll decide whether it's in or out of scope.
2. PubSub diagnostic — required Phase 1 deliverable, not optional. Specifically:

Trigger a test email to trevor@voltsafe.com from a different account.
Verify the webhook fires within ~30 seconds.
If it doesn't, diagnose: is the watch still active? Is GMAIL_PUBSUB_TOPIC correctly pointing at the new GCP project? Is the webhook URL reachable from outside?
Report findings. Fix if obvious; flag for separate ticket if non-trivial.
Regardless of push state, implement the 15-second foreground polling fallback so the unified inbox does not depend solely on push.

3. Deep history — soft cap with explicit opt-in for further. 5,000 rows per session, then a "Load older history" affordance that the user clicks to opt into another 5K chunk. Honest about cost, doesn't surprise users with rate-limited experiences, doesn't auto-backfill 10 years of history because someone's mouse wheel got stuck.
4. Pre-existing bulk-mark-read and bulk-archive bugs — fix in this PR. Both 1-line additions per your estimate. The unified inbox makes the visual flash much more obvious, so these bugs essentially become regressions if not fixed.
5. New-user default — auto 90-day backfill on OAuth completion, with visible progress. Kick it off on first OAuth completion. Show a small progress indicator (Importing your last 90 days of email... 1,247 of ~5,000). Make it abortable from the UI. Don't make it silent — a silent backfill on a fresh connection makes users think the product is broken when they see an empty inbox and watch disk usage spike.
6. Virtualization — Phase 2. Don't introduce @tanstack/react-virtual in this PR. Add a Phase 2 trigger condition in the project notes: "virtualize if user-reported scroll lag accumulates OR any user's inbox crosses 10K visible rows."
7. Multi-account — preserve existing "all" sentinel behavior. No changes to multi-account handling. Don't break what works.
Two additions to the plan
A. Admin recovery endpoint. Add an admin-only diagnostic + recovery endpoint that can:

Inspect a user's sync state (last_webhook_at, pending mutation queue depth, count of backfilled rows, last full sync time).
Trigger a fresh backfill for a user.
Force a full re-sync from Gmail if local state has drifted.

This is operator-facing, not user-facing. Without it, the only recovery option for a user in a bad state is direct SQL access. Build it now while the architecture is fresh.
B. Update MIGRATION_RECOVERY.md (or equivalent project notes) with findings. Specifically:

Document the resolved state of GMAIL_PUBSUB_TOPIC (confirmed working / found broken / fixed).
