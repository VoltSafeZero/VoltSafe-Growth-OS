SEV-1 FOLLOW-UP — CURRENTS API ROUTES EXIST IN SOURCE BUT ARE NOT REGISTERED AT RUNTIME

Do not roll back.
Do not republish.
Do not modify production data.
Do not begin feature work.
Do not change the Currents schema or rebuild Currents.

Confirmed production failure:

Every original Currents API request falls through to the SPA shell:

- /api/current/channels
- /api/current/channels/:id/messages
- /api/current/search
- /api/current/attachments
- /api/current/channels/:id/members

Observed response:

- HTTP 200
- Content-Type: text/html
- Body: index.html

Positive control:

- /api/leads returns HTTP 401 application/json
- therefore the server is alive, /api routing works generally, and this failure is specific to /api/current/*

The original Currents production data is intact:

- current_channels = 15
- current_messages = 43
- current_conversations = 7
- replacement currents_* tables are absent

The problem is runtime route registration, not missing data.

==================================================
PART 1 — PROVE WHETHER CURRENTS ROUTES REGISTER
==================================================

Read-only investigation first.

Locate every /api/current/* registration in server/routes.ts.

For each route group, report:

- surrounding function/block
- whether it is inside an if/else, try/catch, feature flag, return branch, or IIFE
- whether execution can skip over it
- whether it appears before or after any return from registerRoutes()
- whether it depends on a migration, schema check, environment variable, or imported service
- whether an exception earlier in registerRoutes() can prevent the block from being reached

Do not rely on grep count alone.

Produce a control-flow trace from:

registerRoutes() entry
→ first route registration
→ Currents route block
→ registerRoutes() return

Show every possible early return or thrown exception before the Currents block.

==================================================
PART 4 — COMPARE SOURCE AND BUNDLE
==================================================

Confirm for each Currents route:

- route exists in server/routes.ts
- route exists in dist/index.cjs
- registration block executes at runtime
- route appears in Express router stack
- route responds with JSON/401 rather than SPA HTML

If it exists in source and bundle but not router stack, identify the exact runtime control-flow reason.

If it appears in router stack but still falls through, inspect:

- malformed path pattern
- router mounted under another prefix
- Express version/path-to-regexp incompatibility
- registration on a different Express app/router instance
- middleware consuming or rewriting the request
- route method mismatch
- route ordering

Do not guess.
