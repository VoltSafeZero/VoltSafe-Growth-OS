2. First batch target list

Apply Phase 16 controls to these first, unless audit proves a route does not exist:

A. Board Pack
- finalize board pack
- archive board pack
- markdown export
- investor update draft generation

Requirements:
- keep requireBoardPackAccess
- record audit event for finalize/archive/export/draft
- draft/export remain copy_only: true
- no auto-send

B. Capital / Investor Portal
- investor portal token revoke
- investor portal token regenerate/create
- Capital export routes if present
- Capital delete/archive routes if present

Requirements:
- keep requireCapitalAccess
- require confirmation for revoke/regenerate/delete/archive/export where appropriate
- record audit event
- never log token values or investor memo text

C. Mail
- send email
- forward email
- delete email
- archive email
- bulk label/archive/delete if present

Requirements:
- keep requireAuth and mailbox ownership checks
- require explicit action/confirmation for send/forward/delete/bulk destructive actions
- record audit event
- never log email body, subject content if sensitive, OAuth tokens, or recipient body text
- audit metadata may include message count, route, action type, mailbox owner id

D. Currents
- archive/delete channel
- private channel membership add/remove
- delete message if present

Requirements:
- keep membership/admin checks
- require confirmation for private channel membership changes and archive/delete actions
- record audit event
- never log message body or private channel content

E. Admin/User Management
- role/permission changes
- user disable/delete
- invite/remove user if present

Requirements:
- keep requireAdmin or stronger
- require confirmationText for critical changes:
  - CHANGE PERMISSIONS
  - DISABLE USER
  - DELETE USER
- record audit event
- never log secrets or invite tokens

3. Backend implementation pattern

For each selected route:

- import recordHighRiskAction or recordSecurityAuditEvent
- preserve existing guard
- validate confirmation if required
- perform object-level authorization as already done
- record attempted/denied/succeeded/failed events where practical
- do not throw from audit helper
- do not store sensitive payloads

Example structure:

- if confirmation missing:
  - record denied/failed audit event if actor exists
  - return 400 with clear message

- after successful action:
  - record succeeded audit event with safe metadata

- on caught failure:
  - record failed audit event with safe metadata
  - return existing error pattern

Safe metadata only:
- ids
- counts
- route
- action type
- target type
- status
- booleans
- safe labels

Never audit:
- email bodies
- Currents message bodies
- private DM content
- OAuth tokens
- webhook tokens
- investor memo text
- Board Pack full sections
- Capital confidential notes
- passwords
- API keys

4. Frontend implementation pattern

client/src/components/security/confirm-high-risk-action.tsx

Apply to highest-risk visible actions first:

- Board Pack finalize/archive/export

- Mail send/forward/delete/bulk destructive actions
