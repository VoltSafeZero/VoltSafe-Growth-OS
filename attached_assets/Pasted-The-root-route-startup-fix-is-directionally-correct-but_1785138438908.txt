==================================================

The current implementation reportedly:

- starts listening
- registers API routes and frontend
- then launches all migrations in a fire-and-forget background task

This may allow API requests or jobs to query missing tables or columns before migrations complete.

Audit every startup migration and classify it:

A. CRITICAL BEFORE READY
Required for:
- authentication
- sessions
- user permissions
- core routing
- primary calendar APIs
- primary Mail APIs
- Cortex Domain Watch APIs
- any endpoint likely to be called immediately after login

B. REQUIRED BEFORE A DEPENDENT JOB
Required before:

- Cortex auto-ingestion

- calendar polling
- automation schedulers
- engagement schedulers
- help-centre indexing
- CRM linking

C. NONCRITICAL AFTER READY

- optional indexes
- backfills
- repair jobs
- analytics aggregation
- sample data checks
- nonessential indexing

Do not launch every migration blindly in one background task.

==================================================
PART 3 — REQUIRED STARTUP MODEL
==================================================

Use this sequence:

1. Create Express.
2. Register:
   - /healthz
   - /readyz
   - /api/version
3. Register API routes.
4. Register frontend static/Vite serving.
5. Start listening.
6. Run critical schema migrations in an ordered orchestrator.
7. Mark /readyz ready only after critical schema verification passes.
8. Start dependent background jobs only after their required migrations succeed.
9. Run noncritical migrations and repairs afterward in bounded background tasks.

The frontend may load while readiness is starting.

However, APIs requiring unavailable schema must respond with a controlled HTTP 503, not produce database query failures.

Example:

{
  "error": "Service temporarily unavailable",
  "status": "starting"
}

PART 4 — PREVENT SCHEMA RACES
==================================================

Confirm these jobs cannot start before their required schema exists:

- Gmail incremental sync
- Cortex auto-ingest
- Capital email linker
- calendar synchronization
- automation scheduler
- engagement scheduler
- search/indexing workers

Use explicit gates such as:

await requiredSchemaReady;

or start the job only after the relevant migration resolves.

Do not use arbitrary delays.

Do not allow this pattern:

void migrateRequiredTable();
startJobThatQueriesRequiredTable();

Required pattern:

await migrateRequiredTable();
startJobThatQueriesRequiredTable();

A failure in an optional job must not prevent the frontend from loading.

A failure in required schema must keep /readyz unhealthy and prevent dependent jobs from starting.
