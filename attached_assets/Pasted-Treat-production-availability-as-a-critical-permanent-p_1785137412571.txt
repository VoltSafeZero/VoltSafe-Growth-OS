Treat production availability as a critical, permanent platform requirement for VoltSafe CMS.

The production .app being unavailable, returning startup JSON, serving a blank page, entering a crash loop, or being replaced by a failed deployment is unacceptable.

Do not make a temporary patch. Build a production-safety architecture that prevents application changes from taking the live site down and gives us immediate, actionable evidence whenever infrastructure outside our control fails.

==================================================
CORE AVAILABILITY OBJECTIVE
==================================================

A new release must never replace the currently working production deployment unless the new release is proven healthy.

Required deployment behavior:

1. Build the new release.
2. Start the new release separately from the current production instance.
3. Run startup migrations safely.
4. Run automated health and smoke checks against the new instance.
5. Promote traffic only after all required checks pass.
6. If any required check fails:
   - do not promote
   - keep the previous production deployment live
   - clearly report the failure
7. If the new release becomes unhealthy immediately after promotion:
   - automatically roll back to the most recent verified healthy deployment where platform support allows
   - otherwise provide an immediate one-click rollback procedure

Do not allow a failed deployment to replace a healthy deployment.

==================================================
HEALTH ENDPOINTS
==================================================

Maintain three clearly separate concepts.

1. Liveness

GET /healthz

Must return HTTP 200 as soon as the Node process is listening.

Example:

{
  "status": "ok",
  "process": "running",
  "uptimeMs": 1234
}

It must not depend on:

- the database
- authentication
- Gmail
- calendar sync
- Cortex
- OpenAI
- help-center indexing
- background jobs
- frontend rendering

2. Readiness

GET /readyz

Return 503 until all truly critical startup work is complete.

Return 200 after the app can safely serve authenticated production traffic.

Example while starting:

{
  "status": "starting",
  "criticalChecks": {
    "database": "pending",
    "requiredSchema": "pending"
  }
}

Example when ready:

{
  "status": "ready",
  "criticalChecks": {
    "database": "ok",
    "requiredSchema": "ok"
  }
}

3. Frontend smoke check

GET /

Must return the VoltSafe HTML application.

It must never return:

{
  "status": "starting"
}

Startup status belongs only at /readyz.

==================================================
STARTUP ARCHITECTURE
==================================================

Classify every startup operation.

CRITICAL:

Only tasks required for the application to safely serve core authenticated requests.

Examples may include:

- production database connection
- required core schema migrations
- essential authentication schema
- required application configuration validation

NONCRITICAL:

Must never block the frontend or deployment promotion indefinitely.

Examples:

- Gmail incremental sync
- Cortex enrichment
- calendar background synchronization
- help-center indexing
- search reindexing
- optional backfills
- seed data checks
- scheduled automations
- engagement scanning
- CRM enrichment
- analytics aggregation

Correct sequence:

1. Create Express app.
2. Register /healthz, /readyz, and /api/version.
3. Register application API routes.
4. Register frontend static/Vite middleware.
5. Register SPA fallback.
6. Start listening on the assigned port.
7. Run critical startup tasks with explicit timeouts.
8. Mark readiness ready when critical tasks succeed.
9. Start noncritical jobs asynchronously afterward.
10. Log failures without crashing the web process.

No noncritical task may hold the site in “starting.”

==================================================
STARTUP TIMEOUTS
==================================================

Every critical startup operation needs:

- an explicit timeout
- clear error logging
- a defined failure state
- no infinite pending state

Examples:

- database connection timeout
- migration timeout
- schema verification timeout

If a critical operation exceeds its timeout:

- mark readiness as failed
- keep liveness responding
- log the exact task and error
- do not promote the deployment
- do not return startup JSON from /

Noncritical jobs must time out independently and continue retrying according to a controlled policy.

==================================================
DATABASE RESILIENCE
==================================================

The production database must not cause the frontend to disappear.

Implement:

- bounded connection attempts
- exponential backoff with a maximum delay
- safe connection-pool settings
- query timeouts
- migration advisory locking where appropriate
- idempotent migrations
- clear migration success/failure logs
- no competing migration runners
- no unhandled rejected migration promises

Required schema migrations must complete before readiness becomes healthy.

Optional migrations/backfills must not block readiness.

Do not run large data backfills synchronously during deployment startup.

Move large backfills to:

- resumable background jobs
- explicit admin maintenance actions
- or bounded batches with progress tracking

==================================================
MIGRATION SAFETY
==================================================

Audit every startup migration.

For each migration, classify it as:

- required before readiness
- safe after readiness
- one-time data repair
- optional indexing
- deprecated

Prevent these failure modes:

- migration launched fire-and-forget before dependent code queries the table
- Gmail/Cortex/calendar job starts before its required table exists
- two instances run incompatible migration work simultaneously
- a failed migration is swallowed
- long index creation blocks deployment
- startup reports ready before required schema exists

Add one canonical migration orchestrator with:

- ordered execution
- per-migration timing
- success/failure reporting
- advisory lock
- idempotency
- timeout controls
- final schema verification

==================================================
PRE-PROMOTION RELEASE GATE
==================================================

A deployment is promotable only if all checks pass.

Required automated checks against the candidate instance:

1. GET /healthz returns 200.
2. GET /readyz returns 200 within the allowed startup window.
3. GET /api/version returns the expected commit SHA.
4. GET / returns 200 and Content-Type includes text/html.
5. Returned HTML contains the VoltSafe frontend root and expected asset references.
6. At least one JavaScript asset returns 200.
7. At least one CSS asset returns 200 when applicable.
8. A safe unauthenticated API route behaves correctly.
9. Database schema verification passes.
10. No startup crash loop exists.
11. No unhandled rejection or uncaught exception appears.
12. No critical migration error appears.

If any check fails, the deployment must not promote.

==================================================
PROCESS-LEVEL RESILIENCE
==================================================

Add global handling for:

- uncaughtException
- unhandledRejection

Do not blindly continue after all fatal exceptions.

Classify failures:

- recoverable background-job failure:
  log, retry, continue serving

- fatal core-process failure:
  log clearly and exit so the platform restarts or preserves the old deployment during candidate verification

Never leave a half-alive process that responds incorrectly forever.

Add graceful shutdown handling for:

- SIGTERM
- SIGINT

On shutdown:

- stop accepting new work
- close HTTP server
- close database pool
- stop schedulers
- finish bounded in-flight requests
- exit cleanly before platform timeout

- open a circuit temporarily
- stop hammering the service
- continue serving the VoltSafe UI
- show degraded status in admin diagnostics
- retry later
