Expand VoltSafe CMS contextual help/info system across main tabs, subtabs, and fields.

Context:
The app now has info/help icons for main sidebar tabs, which is good. But screenshot shows:
- Main tabs have help icons.
- Subtabs like Capital → Command Center, Investors, Rounds & Commitments, Follow-Ups, Data Room, Engagement, Reports, AI Copilot, Updates & Reviews do NOT consistently have help/info icons.
- Actual fields/cards inside those subtabs do NOT have contextual help.
- Existing help copy is too vague. Example: Capital says "Fundraising workspace — investor pipeline, data room, follow-ups, and board reporting." That explains what it is, but not what the user should do, how to use it, or why it matters.

Required outcome:
Create a deeper, role-aware contextual help system that guides users at 3 levels:

1. Main tabs
2. Subtabs / child navigation items
3. Actual page fields, cards, forms, metrics, buttons, and workflows

The help should answer:
- What is this?
- What should I do here?
- Why does it matter?
- How often should I update it?
- Who owns it?
- What good looks like
- Common mistakes to avoid
- Related next action

PART B — Improve help content quality

Replace vague one-liners with useful guidance.

Each help entry should support richer structure:

Suggested schema:
{
  title: string,
  summary: string,
  whatToDo: string[],
  whyItMatters: string,
  owner: string,
  updateCadence: string,
  goodLooksLike: string[],
  commonMistakes: string[],
  relatedActions: string[]
}

If current FieldHelp only supports title/body/category, extend it cleanly.

Example for Capital:
Title: Capital
Summary: Manage VoltSafe fundraising, investor relationships, round progress, data-room assets, and board/investor updates.
What to do:
- Keep every investor assigned to a stage.
- Log follow-ups after every investor interaction.
- Keep round targets, committed capital, and probability-weighted pipeline current.
- Upload current pitch deck, financial model, diligence files, and monthly updates.
Why it matters:
- This prevents investor conversations from slipping, keeps the raise forecast real, and gives leadership one source of truth for capital strategy.
Owner:
- CEO / CFO
Update cadence:
- Weekly during active fundraising; immediately after investor conversations.
Good looks like:
- Every active investor has a next step and owner.
- No stale follow-ups older than 7 days.
- Data room has current docs.
- Round progress matches actual commitments.
Common mistakes:
- Leaving investors in generic stages.
- Not recording soft commitments.
- Letting old decks/models remain live.
Related actions:
- Add investor
- Create follow-up
- Upload data-room file
- Generate investor update

Example for Capital → Rounds & Commitments:
Title: Rounds & Commitments
Summary: Track each financing round, target amount, committed capital, investor status, close probability, and key dates.
What to do:
- Create one active round for the current raise.
- Add target amount, valuation assumptions, close timeline, and round owner.
- Link investors and commitments to the correct round.
- Update soft circled, verbally committed, signed, and wired amounts separately.
Why it matters:
- Leadership needs to know the real fundraising gap, not the happy spreadsheet version.
Owner:
- CEO / CFO
Update cadence:
- After every investor update; minimum weekly during raise.
Good looks like:
- Target, committed, soft circled, and remaining gap are clear.
- Every commitment has an investor, amount, stage, owner, and close date.
Common mistakes:
- Mixing soft interest with signed commitments.
- Counting the same investor twice.
- Forgetting to update close probability.
Related actions:
- Add round
- Add commitment
- Review investor follow-ups
- Generate board update

PART E — Role-aware help copy

Help should adapt slightly based on user role where useful.

Examples:
Executive:
- Explain how the page affects strategy, cash, revenue, investors, and decision-making.

Sales:
- Explain what actions drive pipeline, follow-ups, and customer movement.

Engineering:
- Explain what is needed for delivery, blockers, certification, releases, and QA.

Admin:
- Explain system impact and permissions risk.

Advisor:
- Explain what they can view, comment on, or contribute without exposing admin/sensitive controls.

Do not overcomplicate this in v1. Start with default help copy, then optionally add role-specific notes where obvious.

PART G — UI behavior

Popover should be readable and useful:
- Wider than the current tiny tooltip if needed.
- Support headings and bullets.
- Do not run off-screen.
- Scroll internally if long.
- Close on outside click and Escape.
- Remain accessible by keyboard.
- Use aria-label / aria-describedby.
- Light/dark mode support.
- Avoid covering the exact field the user is trying to understand where possible.
