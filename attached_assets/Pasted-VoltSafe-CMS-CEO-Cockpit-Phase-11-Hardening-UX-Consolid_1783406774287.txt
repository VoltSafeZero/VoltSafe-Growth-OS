2. Permission audit

Verify and test these access rules:

General CEO Cockpit:
- admin-only unless explicitly scoped otherwise

CEO/CFO-only:
- Board / Investor Operating Pack
- Runway Intelligence
- Funding Forecasting
- Capital/Funding sections
- any investor/fundraising data

Capital-gated:
- capital-sensitive sections must remain hidden if user lacks capital access

Non-admins:
- must not see CEO Cockpit toggle
- must not fetch CEO Cockpit APIs
- must not access action queue, briefing, execution, forecasting, board pack routes

Tests must prove:
- unauthenticated users receive 401
- non-admin users receive 403
- normal admins cannot access CEO/CFO-only routes
- CEO Trevor can access CEO/CFO-only routes
- CFO Scott Carlson can access CEO/CFO-only routes
- capital sections are hidden if capital permission fails
- frontend hides restricted tabs/panels

3. Migration hardening

Review every startup migration added in Phases 5–10.

Ensure:
- CREATE TABLE uses IF NOT EXISTS
- CREATE INDEX uses IF NOT EXISTS
- ALTER TABLE ADD COLUMN is protected by information_schema check or equivalent safe pattern
- no migration uses undefined pool
- all migrations use the correct in-scope db executor pattern
- every migration logs success/failure clearly
- no migration silently swallows errors
- no migration can fail because an index/table/column already exists
- no migration drops production data
- no migration rewrites production data unnecessarily

Add or update tests for migration safety.

4. UI consolidation

The Today → CEO Cockpit view likely now has many panels.

Improve the layout without removing functionality.

Preferred structure:
- top-level CEO Cockpit navigation:
  - Overview
  - Actions
  - Briefing
  - Execution
  - Forecasting
  - 1:1s
  - Board Pack

Each top-level area should render only when selected.
Avoid rendering every heavy panel at once.

Requirements:
- default tab should be Overview
- lazy fetch data only for the active tab
- keep existing section components, but organize them cleanly
- preserve all existing test IDs where practical
- do not break Phase 4–10 tests
- mobile layout must remain usable
- loading states should be clear
- empty states should be executive-clean

5. Performance hardening

Audit all CEO Cockpit API routes and services.

Ensure:
- each query has a LIMIT where appropriate
- each section has try/catch isolation where appropriate
- failures in one section do not kill the whole cockpit
- frontend queries are lazy / enabled only when active
- no panel fetches data if hidden or inaccessible
- no excessive polling
- no external APIs
- no unnecessary N+1 query patterns if obvious
- large JSON sections are capped

Add defensive empty states.

6. Privacy and safety audit

Prove:
- private Currents channels excluded
- DM bodies not broadly exposed
- no sendEmail in CEO Cockpit / briefing / execution / forecast / board pack scoped route blocks
- no sendMessage auto-send
- no Gmail draft creation unless explicitly requested elsewhere
- copy-only drafts remain copy_only: true
- no keystroke tracking
- no invasive productivity scoring
- no shaming language
- no sensitive text stored in localStorage
- snooze/localStorage stores only IDs and timestamps

Banned user-facing language:
- lazy
- failing
- weak performer
- poor performer
- blame
- underperforming

Use neutral language:
- blocked
- stale
- drifting
- needs check-in
- follow-up suggested
- support needed
- owner load risk
