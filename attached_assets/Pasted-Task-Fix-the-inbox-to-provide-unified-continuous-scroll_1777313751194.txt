Task: Fix the inbox to provide unified continuous scrolling across live Gmail and local archive, like Gmail / Superhuman / Spark. Currently the UI shows "Live Gmail INBOX: 22 · Local archive: 1,191" with a toggle to switch between them. This needs to become one continuous inbox where the user scrolls down indefinitely without thinking about live vs. archive.
This is an investigation and planning task — do not write the fix yet. Inspect the current architecture, propose a plan, then wait for my approval before implementing.

Proposed plan
After investigation, propose a plan for the fix that addresses these requirements:
Goal state:

Single continuous inbox view per user. No "live vs. archive" toggle, no "switch to local archive" link.
New emails from Gmail appear at the top automatically (live sync, ideally via Gmail's push notifications / Pub/Sub if configured, or via polling every N minutes if not).
Scrolling down loads progressively older emails from the local archive.
Once the user scrolls past the bottom of what's locally cached, the app fetches the next chunk from Gmail's API and appends it to the local archive seamlessly. From the user's perspective, scroll continues without a visible "loading historical emails" wall.
State changes (read, star, archive, delete) update both the local cache and Gmail, with eventually-consistent two-way sync.
Works for any user who connects Gmail — not just my account.

Performance constraints:

Initial inbox render must be fast (≤ 500ms perceived load) for users with 100K+ archived emails.
The DB query for "next 50 emails older than X" must be index-supported. Confirm whether the existing schema has an index on date_received DESC (or equivalent) — if not, propose adding one.
Backfill from Gmail must respect Gmail API rate limits (250 quota units per user per second per Google's docs; each messages.get is ~5 units).

Specific architectural choice — confirm or counter:
I'm leaning toward Option A (single source of truth in local DB): live Gmail becomes a sync source that appends to the local DB. The UI reads exclusively from the local DB. Both new emails and historical backfill flow into the same store.
The alternative is Option B (query-time merge) where the UI queries live Gmail for the top of the list and falls through to local archive lower down. This is more complex (pagination across heterogeneous sources, timestamp tiebreaking, dual state-tracking) and I don't think it's worth it.
If you have a strong reason to prefer B, make the case. Otherwise, plan for A.
Sync architecture for A:

New emails: ideally Gmail push (Pub/Sub) for real-time, with polling as a fallback. The standing rule from MIGRATION_RECOVERY.md flagged that GMAIL_PUBSUB_TOPIC was misconfigured post-migration — confirm current state of the Pub/Sub integration.
Historical backfill: triggered on-demand when the user scrolls past locally-cached content. Fetches next N emails older than the current oldest cached date, writes to DB, returns them to the UI.
State sync (two-way): when the user marks read/starred/archived in this UI, the change is queued and pushed to Gmail. Periodic full-state reconciliation (every N minutes) ensures local and Gmail stay aligned even if individual operations failed silently.
