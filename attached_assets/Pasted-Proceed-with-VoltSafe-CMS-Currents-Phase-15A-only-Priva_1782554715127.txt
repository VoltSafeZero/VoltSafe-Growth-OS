Goal

Add the foundation for private channels in Currents.

Currents currently supports public channels, archived channels, DMs, group DMs, attachments, reactions, typing, presence, participants, structured items, AI summaries, tasks, and slash commands.

Phase 15A should add private channel visibility and membership controls for internal users only.

Keep this scoped to internal private channels. Do not add guests or external collaborators.

Data model

Add if not already present:

current_channel_members

Fields:

* id
* channel_id
* user_id
* created_at
* created_by

Constraints:

* unique (channel_id, user_id)
* FK channel → current_channels(id) ON DELETE CASCADE
* FK user → users(id) ON DELETE CASCADE

Add to current_channels:

* is_private BOOLEAN NOT NULL DEFAULT FALSE

Migration must be idempotent.

Existing public channels remain public.

Product behavior

Public channels

No behavior change:

* visible to all authenticated internal users
* readable by all
* writable unless archived
* existing archive/read-only behavior preserved

Private channels

Only members can:

* see the channel in sidebar
* open the channel
* read messages
* post messages
* reply in threads
* react
* upload/list/download attachments
* see pins
* search messages
* see mentions from that channel
* see structured items from that channel
* see participant list
* receive notifications
* use slash commands in that channel

Admins can create/manage private channels.

Decision:

* Admins may either bypass membership for management only, or must be members to read/post.
* Preferred: admins can manage channel membership/settings, but reading/posting private channel content requires membership unless explicitly added.

Document whichever behavior is implemented.

Backend requirements

Create helper logic if useful:

* canViewChannel(userId, channelId)
* canPostToChannel(userId, channelId)
* isChannelMember(userId, channelId)

Rules:

1. Public channel: authenticated users can view/post unless archived.
2. Private channel: only members can view/post.
3. Archived channel: no write actions regardless of public/private.
4. Admin-only channel management routes remain admin-only.
5. Membership checks must be server-side. Frontend hiding is not enough.

Channel management routes

Update create/edit routes to support:

{
  "name": "Leadership",
  "description": "Private leadership discussion",
  "isPrivate": true,
  "memberIds": [1, 2, 3]
}

Rules:

1. Admin only.
2. Create private channel with creator/admin as member automatically.
3. Validate member IDs.
4. Exclude suspended/deactivated users.
5. Deduplicate members.
6. Preserve existing public channel create behavior.
7. Editing a channel can toggle public/private only if safe.
8. Membership updates should not break archived channels.

If toggling public/private is too risky for Phase 15A, support only setting privacy at creation and editing members afterward. Document the limitation.

New membership routes

Add admin-only routes:

GET /api/current/channels/:slug/members

PUT /api/current/channels/:slug/members

or equivalent.

Rules:

1. Requires admin.
2. Channel must exist.
3. Works for private channels.
4. For public channels, either return empty/formal members or allow preparing members before making private.
5. Validates users.
6. Excludes suspended/deactivated users.
7. Cannot remove the last member from a private channel.
8. Returns sorted member list.
9. No private fields leaked.
