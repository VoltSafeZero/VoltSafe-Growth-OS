Part A — mail-permissions CSRF/origin test harness

Investigate the mail-permissions failures.

Determine:

1. Which route(s) fail.
2. Whether failure is due to missing CSRF token.
3. Whether failure is due to missing Origin/Referer header.
4. Whether the test harness is calling routes differently than the app does.
5. Whether production behavior is correct.

If production behavior is correct, fix the test harness only.

Acceptable fixes:

* add the correct Origin header in the test request
* add a valid CSRF token flow in the test setup
* use the same authenticated request helper used by other passing Gmail route tests
* document why CSRF/origin guard must remain enabled

Do not bypass or weaken the production guard.

Part B — tracking-proof live Gmail-send dependency

Investigate:

* tracking-proof
* tracking-multi-proof

Determine whether these tests are:

1. true automated unit/integration tests, or
2. live external service proofs that require real Gmail send behavior.

If they require live Gmail sends, do not make them part of normal test readiness.

Preferred fix:

1. Add a clear environment guard such as RUN_LIVE_GMAIL_PROOF=true.
2. If the env var is missing, skip with an explicit message:
    skipped: requires RUN_LIVE_GMAIL_PROOF=true and live Gmail credentials
3. Keep the live proof available for manual runs.
4. Do not mark skipped live proof as a product failure.
5. Add or confirm a separate mocked tracking test exists for normal CI/dev readiness.

If no mocked tracking test exists, propose one but do not build a large new harness unless small and safe.

Part C — stale workflow-status artifacts

Investigate any workflow/status panel that still reports old failures even when direct tests pass.

Determine:

1. whether the status is stale
2. whether it reflects a previous run
3. whether the workflow command differs from the direct test command
4. whether the workflow needs updated test commands or labels

Only fix if the change is clearly test metadata/command hygiene.
