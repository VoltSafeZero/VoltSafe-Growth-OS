CORTEX IS STILL FUNDAMENTALLY BROKEN. FIX THE ACTUAL INGESTION + RETRIEVAL PIPELINE, NOT THE WORDING OF THE RESPONSE.

Observed failure:
A user pasted important URLs so Cortex could learn their specific content. When asked:

“What did you learn today from what you were fed? Did you not ingest the specific linked content from the ingested url's?”

Cortex answered that it learned from “various web resources” but “does not have access to the specific content of those linked URLs.”

That response proves Cortex is only remembering URL names, categories, domains, or metadata. It is not reliably fetching, extracting, storing, indexing, retrieving, and citing the actual content.

This is now the fifth attempted fix. Do not apply another cosmetic patch.

PRIMARY REQUIREMENT

Every URL submitted to Cortex must move through a verifiable ingestion pipeline:

URL submitted
→ URL normalized and validated
→ source fetched
→ meaningful content extracted
→ video/audio transcribed where applicable
→ content chunked
→ chunks embedded/indexed
→ source record persisted
→ ingestion status shown
→ retrieval tested
→ Cortex answers using the stored source content

Cortex must never claim it learned from a source unless usable source content was actually stored and indexed.

Report the root cause before making the fix, but continue immediately with the implementation.

- ready

Do not mark a source “ready” merely because the URL record was saved.

A source may only become “ready” when:

- meaningful content was extracted
- at least one usable chunk was stored
- the chunk is present in the retrieval index
- a verification query can retrieve that source

3. FIX SOURCE FETCHING AND EXTRACTION

Implement source-specific extraction.

Normal webpages:
- follow redirects safely
- extract article/body content
- remove navigation, cookie banners, footers, advertisements, and repeated boilerplate
- preserve headings, lists, captions, dates, and meaningful context
- reject pages where only a title or tiny amount of text was extracted

YouTube:
- resolve the video ID
- retrieve captions/transcript when available
- store transcript text and timestamps where possible
- if captions are unavailable, mark the source partial or failed with a clear reason
- never pretend the video was learned from when only its title or description was captured

PDFs:
- download and extract selectable text
- preserve page references
- use the project’s supported document extraction method
- mark scanned/unreadable PDFs clearly instead of silently succeeding

LinkedIn and other restricted sites:
- attempt only lawful, supported retrieval methods
- if the page blocks extraction or requires authentication, mark it blocked or partial
- show the user exactly what was and was not captured
- do not claim the post/article was ingested if only Open Graph metadata was available

Redirected URLs:
- retain both original and final resolved URL
- deduplicate using canonical URL and content hash

Minimum usable-content threshold:
A source must not become retrieval-ready if it contains only a page title, description, domain name, or a few metadata fields.

4. ADD BACKGROUND JOB RELIABILITY

Ingestion must not depend on the browser request staying open.

Implement or repair:

- durable queued ingestion jobs
- retry with bounded exponential backoff
- timeout handling
- idempotency
- duplicate prevention
- job recovery after app restart
- stage-by-stage error recording
- structured logs with source ID and job ID

Do not create duplicate chunks or duplicate sources during retries.

5. FIX CHUNKING AND INDEXING

Store the actual extracted content in retrievable chunks.

Each chunk must include:

- chunk ID
- source ID
- chunk text
- sequence/order
- heading or section
- page number or timestamp when applicable
- token/character count
- embedding/index status
- content hash
- source permissions

Chunking must preserve semantic sections and useful context. Do not split into fragments so small that meaning is destroyed.

All chunks must inherit the source’s access permissions.

6. FIX RETRIEVAL

The current response strongly suggests the answer generator is not retrieving stored content.

For each Cortex question:

- determine whether the question requires the user’s ingested knowledge
- search the stored chunks
- apply the current user’s permission scope
- rank relevant chunks
- pass the best grounded excerpts into the answer model
- require source IDs in the generated answer payload
- return citations linked to the ingested source record

For questions such as:

- “What did you learn today?”
- “What did I feed you today?”
- “Summarize today’s sources.”
- “What did you learn from the NMMA link?”
- “What was in the YouTube video I added?”
- “What did the LinkedIn article say?”

Cortex must search ingestion records by submission date and retrieve the actual stored content from those records.

“What did you learn today?” must be based on sources successfully ingested during the user’s current local calendar day, not generic web knowledge.

7. ELIMINATE HALLUCINATED INGESTION

Add strict grounding rules:

- Cortex cannot say “I learned from X” unless X is retrieval-ready.
- Cortex cannot summarize a source unless retrieved chunks from that source are present in the prompt.
- Cortex cannot list a domain merely because a URL was submitted.
- Cortex cannot imply a blocked or failed URL was ingested.
- Cortex must distinguish:
  - submitted
  - fetched
  - partially extracted
  - fully indexed
  - failed
  - blocked

When nothing usable was retrieved, say plainly:

“I found the URL submission, but its content was not successfully extracted and indexed. Status: blocked/failed. Reason: [specific reason].”

Do not give the generic “I do not have access to specific linked content” answer when the product’s purpose is to ingest linked content.
