EXPAND THE @MENTION SYSTEM ACROSS THE ENTIRE VOLTSAFE CMS

The @mention system must not be limited to CURRENTS and Task HUB.

Build it as a shared, CMS-wide capability that works anywhere a user can write text, add a note, leave a comment, record an update, assign an action, or communicate about a record.

The goal is simple:

When someone writes @Scott, @Terri, @Sanad, @Trevor, or another valid user anywhere in VoltSafe CMS:

1. The name becomes a real user-linked mention.
2. The mentioned user is notified.
3. The notification links directly to the exact record and exact location where they were mentioned.
4. The mentioned user can see what they were asked to do.
5. The mentioned user can acknowledge, view, or complete the callout.
6. The author and relevant users can see the mention status.
7. Every user has one central place to see all their mentions across the entire CMS.

Do not create separate, inconsistent mention systems inside each module.

Build one shared mention service, one shared mention UI component, one shared status model, and one shared mentions feed that every module uses.

global_mentions

- priority

- updated_at

Status values should include at minimum:

- unread
- viewed
- acknowledged
- completed
- dismissed

Do not treat “viewed” and “completed” as the same thing.

Viewing means the user opened the callout.

Completed means the user confirms that the requested action is finished.

A mention may not always require completion, so support lightweight acknowledgement as well.

STRUCTURED CONTENT

Mentions must be stored as structured user references using immutable user IDs.

Example:

{
  "type": "mention",
  "userId": "immutable-user-id",
  "label": "Scott Carlson",
  "mentionId": "global-mention-id"
}

Do not rely on repeatedly parsing raw text such as @Scott.

EXAMPLE

Trevor enters this note on a lead:

The system must:

1. Save Scott as a structured mention linked to Scott’s user ID.

3. Notify Scott.
4. Identify the module as Leads.
5. Identify the exact lead record.
6. Save a preview of the note.

8. Mark the mention viewed when Scott opens it.
9. Allow Scott to click his mention chip or callout control to:
   - Acknowledge
   - Mark complete
   - Add a completion note
10. Show Trevor that Scott viewed and/or completed the callout.

DEEP LINKING

Every global mention must link to the exact destination.

Do not merely open the top-level module.

The deep link must open:

- The correct module
- The correct record
- The correct tab
- The correct comment, note, activity, message, or timeline item
- The correct thread where applicable

Highlight or briefly pulse the exact mention location when the destination opens.

Examples:

- Open the exact lead and scroll to the mentioned lead note.
- Open the exact account and highlight the account comment.
- Open the exact contact timeline entry.
- Open the exact CURRENTS thread reply.
- Open the exact task comment.
- Open the exact investor note.
- Open the exact meeting action item.

If the source item is inside a collapsed panel, expand it automatically.

If the source is paginated or virtualized, load the relevant page or record and scroll to it.

VIEWED, ACKNOWLEDGED AND COMPLETED BEHAVIOUR

When the mentioned user opens the exact destination:

- Automatically mark the mention as viewed.
- Record viewed_at.
- Update the unread count.
- Do not automatically mark it completed.

At the mention location, display a small callout control visible to the mentioned user.

Example:

“@Scott Carlson · Requested review”

Available actions:

- Acknowledge
- Mark complete
- Add response
- Dismiss, where appropriate

When completed:

- Record completed_at.
- Record completed_by_user_id.
- Allow an optional short completion note.
- Visually show completion at the source location.
- Notify the original author that the mention was completed, unless notification preferences disable this.

Examples:

“Scott viewed this 14 minutes ago.”

“Scott acknowledged this.”

“Scott completed this callout.”

“Scott completed this callout: Pricing approved at $12,500.”

Clicking the person’s own mention chip should open the status actions when that person is the mentioned user.

Clicking another person’s mention chip should open their profile or mention-status summary, subject to permissions.

Do not allow unrelated users to mark someone else’s mention completed.

The author, administrators, and authorized managers may be allowed to close or cancel a mention with an audit record.

PERMISSIONS AND RECORD ACCESS

A mention must never bypass existing permissions.

If the mentioned user already has access:

- Save the mention.
- Notify them.
- Deep-link them to the record.

If the mentioned user lacks access:

- Determine whether the author has permission to share the record.
- Explain the minimum access that would be granted.
- Require explicit confirmation before granting access.
- Grant the lowest appropriate permission.
- Log the access change.
- Notify the mentioned user only after access is valid.

Example:

“Scott Carlson does not currently have access to this lead. Mentioning Scott will grant access to this lead and its related account information. Continue?”

Actions:

- Share and mention
- Cancel

Only offer “Mention without sharing” when the mentioned user can legally and technically see enough context for the mention to be useful.

Do not notify users about records they cannot open.

Do not expose the record title, preview text, customer name, financial information, private communication, or other restricted details before permission is granted.

SHARING SCOPE

Use the smallest existing permission scope that makes the mention usable.

Examples:

- Mention in a lead note may grant access to that lead if record-level access exists.
- If access is controlled at account level, grant account-level access only when required and explicitly confirmed.
- Mention in a private project must follow project membership rules.
- Mention in a private channel must follow channel membership rules.
- Mention in an investor record must respect Capital permissions.
- Mention in finance records must respect finance-role restrictions.
- Mention in admin or HR areas must never grant access unless the author has explicit authority.

Do not build @mentions into a permission loophole.

EDITING CONTENT

When content is edited:

- Compare old structured mentions to new structured mentions.
- Notify only users newly added.
- Do not notify unchanged mentions again.
- Mark removed mentions as removed or cancelled.
- Keep audit history.
- Do not delete historical status silently.
- If a completed mention is removed from edited content, retain its audit history but remove it from active lists.
- If the requested action or due date changes, notify the mentioned user only when the change is meaningful.

DELETING CONTENT

If the source message, comment, note, task, or record is deleted:

- Mark the mention source unavailable or deleted.
- Remove it from active work queues.
- Preserve audit history.
- Do not leave broken links without explanation.

Show:

“This mention’s original source was deleted.”

If the entire record is deleted, archive the mention.

DELIVERY STANDARD

This is not merely an autocomplete or notification feature.

It is a CMS-wide callout and accountability system.

A successful implementation means:

- Every real mention is linked to a user.
- Every mention is tied to a specific source.
- Every user can see all their mentions in one place.
- Every mention can be opened directly.
- Every mention can be tracked as unread, viewed, acknowledged, or completed.
- The person who created the mention can see whether it was handled.
- Permissions are never bypassed.
- Today, Daily Execution, and Mission Control all use the same global mention system.
- New VoltSafe CMS modules can adopt mentions through the shared adapter architecture.
