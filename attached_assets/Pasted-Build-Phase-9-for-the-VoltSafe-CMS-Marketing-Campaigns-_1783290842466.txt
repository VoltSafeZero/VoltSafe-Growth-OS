Build Phase 9 for the VoltSafe CMS Marketing / Campaigns module: Branching Automations.

Context:
VoltSafe CMS Marketing/Campaigns now includes:

* Campaign CRUD
* Audience segments
* Real recipient enrollment
* Manual campaign sending
* Automated linear drip sequences
* Open/click tracking
* Public unsubscribe and preference center
* CASL/CAN-SPAM compliance
* Compliance preflight and send-time enforcement
* Account Heat Score
* Buying Committee Intelligence
* Reply Classification
* Sales task creation from reply classifications
* Inbound Reply Ingestion + Campaign Thread Matching
* Phase 8 audit/hardening completed:
    * sent-message idempotency fixed with unique provider_message_id
    * sender validation added for thread/reference matching
    * unsubscribe replies now suppress contacts
    * unmatched reply received_at index added
    * unmatched status allowlist added
    * stale inbound-ingestion gap comment removed

Goal:
Add simple, safe branching automation to campaign sequences so recipient behavior can influence what happens next.

This phase should enable:

* Stop sequence when recipient replies positively
* Stop sequence when recipient unsubscribes/negative replies
* Create sales task when high-intent reply occurs
* Send technical follow-up if recipient clicks technical asset
* Send ROI/business follow-up if recipient clicks ROI asset
* Move no-engagement recipients to a different follow-up path
* Skip future emails when recipient is already sales-engaged

Do not build a giant visual workflow builder yet. Start with rule-based branching attached to campaign steps.

Rules should be:

* priority ordered
* idempotent
* fail-closed

If a rule already fired for the same recipient and same triggering event, do not fire it again.

3. Default Rules

Add a “Seed Recommended Rules” action that creates default rules:

Rule 1:
Name: Stop on meeting request
Trigger: reply_classification = meeting_request
Action: stop_sequence + create_task

Rule 2:
Name: Stop on interested reply
Trigger: reply_classification = interested
Action: stop_sequence + create_task

Rule 3:
Name: Stop on unsubscribe
Trigger: reply_classification = unsubscribe OR recipient_status = unsubscribed
Action: stop_sequence + suppress_recipient

Rule 4:
Name: Stop on negative reply
Trigger: reply_classification = negative
Action: stop_sequence + add_note

Rule 5:
Name: Send technical follow-up
Trigger: clicked_link where original_url contains technical, install, electrical, UL, CSA, spec, datasheet
Action: send_specific_step or move_to_step for a technical follow-up step if present

Rule 6:
Name: Send ROI follow-up
Trigger: clicked_link where original_url contains ROI, pricing, revenue, billing, savings, calculator
Action: send_specific_step or move_to_step for ROI follow-up step if present

Rule 7:
Name: No engagement nurture path
Trigger: no_open_after_step = step 2 after X days
Action: move_to_step or add_note depending on campaign structure

Keep these defaults simple and editable.

4. Integration Points

Rules should evaluate when:

* campaign_event is created for clicked
* campaign_event is created for opened if needed
* reply classification is created
* unsubscribe happens
* automation tick runs and a recipient is due
* manual send/automated send completes

Minimum required integration:

* On reply classification creation → evaluate reply_classification rules
* On click tracking → evaluate clicked_link rules
* On unsubscribe → evaluate recipient_status/unsubscribe rules
* During automation tick → respect stopped/paused/moved recipient state

6. Send-Specific-Step / Move-To-Step Safety

If a rule sends or moves to a specific step:

* ensure step exists
* ensure step has not already been sent to recipient
* ensure recipient is eligible
* run compliance/suppression checks
* prevent duplicate sends
* do not send if recipient replied high-intent and sequence should stop
* do not send if recipient unsubscribed/suppressed/bounced

If too risky for this phase, implement move_to_step and stop_sequence first, and report send_specific_step as remaining gap.

12. Safety / Compliance

Rules must never override:

* unsubscribe
* suppression
* bounce
* do-not-email
* compliance preflight failure
* duplicate-send protection

If a rule action conflicts with compliance/suppression, skip action and log rule event with action_taken = skipped_compliance.
