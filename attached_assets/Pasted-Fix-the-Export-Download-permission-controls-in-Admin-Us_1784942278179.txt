Fix the Export & Download permission controls in Admin → Users & Roles → User Access.

CONFIRMED BUG

When viewing a non-admin user such as:

- Tiffany Mun
- Advisor
- External

the following permissions appear checked as “Allowed” but cannot be toggled off:

- Export Data (CSV / XLSX)
- Download Attachments
- Generate Reports

The UI note says:

“Admins are always exempt from these restrictions.”

That exemption must apply only when the SELECTED TARGET USER is an admin or master admin.

It must not apply merely because the currently logged-in user performing the edit is a master admin.

==================================================
EXPECTED BEHAVIOR
==================================================

For the selected target user:

1. master_admin / super admin
   - export restrictions are always exempt
   - controls may display as locked/always allowed
   - cannot be disabled

2. admin
   - export restrictions are always exempt
   - controls may display as locked/always allowed
   - cannot be disabled

3. executive
   - editable unless there is an explicit existing business rule stating otherwise

4. manager
   - editable

5. advisor
   - editable

6. engineer
   - editable

7. sales, marketing, finance, operations, analyst, read only, external, etc.
   - editable

For Tiffany Mun, all three controls must be toggleable.

==================================================
INVESTIGATE THE ROOT CAUSE
==================================================

Trace the full flow:

Admin User Management page
→ selected user access panel
→ checkbox/switch component
→ local state
→ mutation
→ API route
→ database persistence
→ user refetch

Look specifically for mistakes such as:

- checking currentUser.globalRole instead of selectedUser.globalRole
- using isAdmin based on the logged-in user
- setting disabled={isAdmin} where isAdmin refers to the editor
- preventing mutation because the editor is master_admin
- rendering checked=true from a role fallback that overrides stored values
- sending the wrong user ID
- using invited user defaults instead of persisted permission values
- optimistic state immediately being overwritten by stale query data
- API silently ignoring false values
- PATCH logic using `value || true`
- destructuring defaults that convert false to true
- SQL update using COALESCE incorrectly
- permission values stored as nullable and interpreted incorrectly

==================================================
IMPORTANT BOOLEAN HANDLING
==================================================

False must be treated as a valid saved value.

Do not use patterns such as:

value || true

or:

permission ? permission : true

Use nullish checks only where appropriate:

value ?? defaultValue

The API must distinguish:

- omitted field = do not change
- true = allowed
- false = explicitly denied

==================================================
TARGET USER VS CURRENT USER
==================================================

Use two clearly separate concepts:

- currentUser / actingUser:
  the authenticated admin making the change

- selectedUser / targetUser:
  the person whose permissions are being edited

Authorization to edit is based on currentUser.

Whether the exemption applies is based on selectedUser.

Example:

Trevor Burgess:
- current user
- master_admin
- authorized to edit

Tiffany Mun:
- selected target user
- advisor / external
- not exempt
- permissions must be editable
