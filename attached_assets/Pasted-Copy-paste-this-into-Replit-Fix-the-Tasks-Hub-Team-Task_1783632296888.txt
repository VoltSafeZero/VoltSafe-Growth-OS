Fix the Tasks Hub / Team Tasks logic. Team Tasks are currently behaving like a board filter for individual users, but that is wrong.

Core rule:
Team Tasks are not the same thing as “someone else’s tasks.” Team Tasks must only include tasks that are explicitly marked with a teamTask / isTeamTask / equivalent Team Task flag.

Problem shown in screenshot:
The Team Tasks board currently appears to show personal/user tasks or grouped user work. That must stop. Individual user tasks belong only in that user’s own Tasks Hub unless they are explicitly flagged as Team Tasks.

Required behavior:

1. Team Tasks board filtering
    Update all frontend and backend logic so:

* Team Tasks board only shows tasks where the Team Task flag is true.
* Team Tasks must never show normal personal tasks.
* Selecting “Team Tasks” in the Switch Board popup must not mean “show everyone’s tasks.”
* Selecting a specific teammate/user should show that user’s visible task board according to permissions, but that is separate from Team Tasks.
* Team Tasks should be visible to all users.

2. Team Task creation behavior
    When a task is created as a Team Task:

* It must be flagged as a Team Task in the database/model.
* It must appear on the global Team Tasks board for all users.
* If assigned to one or more users, it must also land in each assigned user’s own Tasks Hub under the Backlog column by default.
* Once it lands in the assigned user’s Tasks Hub, that assigned user can move it to any column/status they want inside their own board.
* The task must remain visible on the Team Tasks board regardless of which assigned user moves it in their own Tasks Hub.

Important:
If the current data model only has one task row/status, add the smallest safe structure needed to support this distinction. Do not let one user moving a team task in their own Tasks Hub accidentally move the canonical Team Tasks board version for everyone unless the intended design already supports per-user task state.

3. Team Task metadata/audit trail
    For any task flagged as a Team Task, clearly display:

* Who created the Team Task.
* Timestamp of creation.
* Who the task is assigned to.
* Timestamp of assignment.
* If reassigned:
    * who reassigned it,
    * who it was reassigned from,
    * who it was reassigned to,
    * timestamp of reassignment.

This should be visible in the task card or task detail modal. Prefer task card for compact summary and detail modal for full audit trail.

4. Assignment/reassignment logic
    When a Team Task is assigned or reassigned:

* Write an audit event.
* Preserve previous assignment history.
* Do not overwrite history silently.
* If reassigned to a new user, ensure the task lands in that new user’s Backlog if they do not already have it in their own Tasks Hub.
* If removing an assignee, decide based on existing product conventions whether their personal copy/state remains archived/completed/removed, but do not silently delete history.

5. Switch Board popup cleanup
    Update the Switch Board popup labels/logic:

* “My Tasks” = current user’s own tasks, including assigned Team Tasks that landed in their board.
* “Team Tasks” = only tasks explicitly flagged as Team Tasks.
* Individual people = that person’s visible task board, subject to permission rules.
* Do not mix these concepts.

6. Backend/API requirements
    Audit all Tasks APIs involved in:

* fetching board tasks,
* fetching team tasks,
* fetching user tasks,
* creating tasks,
* assigning tasks,
* reassigning tasks,
* updating task status/column,
* task audit/activity feed.

Add or fix server-side filters so Team Tasks are enforced by the backend, not only by frontend filtering.

Expected backend distinction:

* GET /tasks/my or equivalent: returns current user’s tasks, including Team Tasks assigned to them.
* GET /tasks/team or equivalent: returns only tasks with Team Task flag true.
* GET /tasks/user/:id or equivalent: returns visible tasks for that selected user, not the global Team Tasks board.

Use existing route names if different.

7. Frontend requirements
    Update Tasks Hub UI so:

* Team Tasks board uses only the Team Task filtered dataset.
* My Tasks remains current user’s own task board.
* User boards remain user-specific.
* Team Task cards show a visible Team Task badge/flag.
* Team Task cards clearly show creator and assignee.
* Task detail modal shows full audit trail for creation, assignment, and reassignment.
* Assigned Team Tasks appear in the assignee’s Backlog column by default.

8. Data migration / backfill
    If existing tasks need migration:

* Do not mark all existing tasks as Team Tasks.
* Only preserve existing Team Task flags if they already exist.
* If there is no reliable existing flag, default existing tasks to non-Team Tasks.
* Add a safe migration only if needed.
* Do not break existing personal task boards.

9. Tests
    Add regression tests covering:

* Team Tasks board excludes personal tasks.
* Team Tasks board includes only tasks with Team Task flag.
* My Tasks includes personal tasks plus Team Tasks assigned to the current user.
* Team Task assigned to a user lands in that user’s Backlog by default.
* Moving a Team Task in a user’s own board does not incorrectly remove it from Team Tasks.
* Team Task card/detail shows:
    * created by,
    * created timestamp,
    * assigned to,
    * assigned timestamp.
* Reassignment records:
    * reassigned by,
    * from user,
    * to user,
    * timestamp.
* Switch Board popup:
    * My Tasks, Team Tasks, and individual users are separate concepts.
* Existing normal tasks are not accidentally converted into Team Tasks.

    Run:

* Confirm it appears:
    * in Team Tasks board for all users,
    * in assigned user’s Backlog.
* Reassign it.
* Confirm reassignment audit details are visible and timestamped.

Report back with:

* Frontend board logic changes.
* Audit trail behavior.
* Migration/backfill behavior.
* Test pass/fail counts.

The simple rule for Replit: Team Tasks means flagged shared work, not “Trevor looking at everybody’s laundry pile.”
