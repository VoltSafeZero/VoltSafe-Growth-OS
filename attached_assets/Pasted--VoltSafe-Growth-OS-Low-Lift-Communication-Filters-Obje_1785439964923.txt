# VoltSafe Growth OS — Low-Lift Communication Filters

## Objective

Restore the missing Activity Status filtering capability in:

- Leads
- Accounts
- Contacts

Expand it modestly so users can quickly identify records needing communication or follow-up.

This must remain a low-lift implementation.

Prioritize reuse of existing communication data, queries, components, filter patterns, and saved-view infrastructure. Do not build a new communications engine, AI inference system, relationship score, background job, or major database architecture.

## Important Workflow

Before changing code:

1. Find the previous Activity Status filter implementation in git history.
2. Identify why it disappeared.
3. Determine which existing frontend and backend functionality can be restored or reused.
4. Report the proposed low-lift implementation plan.
5. Then implement it unless a major migration or architectural change would be required.

Do not rewrite working systems unnecessarily.

## 1. Activity Status Filter

Add an `Activity Status` dropdown to:

- Leads
- Accounts
- Contacts

Place it in the existing filter area using the same visual style as the other dropdowns.

Options:

- All Active Statuses
- Contacted Today
- Contacted This Week
- Recently Contacted
- VoltSafe Owes Reply
- Waiting for Lead
- No Response
- Dormant
- Never Contacted

### Important Behaviour

`All Active Statuses` must include all activity-based statuses except `Never Contacted`.

It must therefore exclude records that have never had any qualifying inbound or outbound communication.

`Never Contacted` must remain a separate standalone status that users select intentionally.

Do not treat `Never Contacted` as part of `All Active Statuses`.

### Definitions

Use one consistent set of definitions across Leads, Accounts, and Contacts.

- `Contacted Today`
  - At least one qualifying outbound communication from VoltSafe today.

- `Contacted This Week`
  - At least one qualifying outbound communication from VoltSafe during the current calendar week.

- `Recently Contacted`
  - At least one qualifying outbound communication from VoltSafe within the last 30 days.

- `VoltSafe Owes Reply`
  - The most recent qualifying inbound communication is newer than the most recent qualifying outbound communication.

- `Waiting for Lead`
  - The most recent qualifying outbound communication is newer than the most recent qualifying inbound communication.
  - This one status replaces:
    - Waiting for Lead
    - Waiting More Than 3 Days
    - Waiting More Than 7 Days
  - Do not create separate waiting-age statuses.

- `No Response`
  - VoltSafe has sent at least one qualifying outbound communication, but no qualifying inbound response has ever been received.

- `Dormant`
  - No qualifying inbound or outbound communication within the last 60 days.
  - Include records that were previously contacted but have since gone inactive.
  - Do not classify Never Contacted records as Dormant.

- `Never Contacted`
  - No qualifying inbound or outbound communication exists.

Reuse any already-approved definitions in the current codebase where they differ, but document those differences before implementation.

## 2. Waiting for Lead Ordering

When `Waiting for Lead` is selected, automatically sort matching records by the date and time VoltSafe began waiting.

Required order:

- Most recent waiting record first
- Oldest waiting record last

Use the most recent qualifying outbound communication that has not yet received a newer qualifying inbound response as the waiting timestamp.

This automatic ordering must apply unless the user explicitly selects another sort option.

The UI should make the automatic ordering understandable, for example by showing:

- `Waiting Since`
- `Most Recent Waiting`

Do not create separate status buckets for 3-day, 7-day, or longer waits.

Where practical, display a readable waiting age such as:

- Waiting 2 hours
- Waiting 3 days
- Waiting 12 days

Reuse an existing relative-time component if one already exists.

## 3. Communication Filter

Add one additional dropdown labelled `Communication`.

Keep this as a single dropdown rather than building a large advanced-filter panel.

Options:

- All Communications
- Last Activity: Email
- Last Activity: Call
- Last Activity: Meeting
- Last Activity: SMS
- Last Activity: Note
- Last Activity: Inbound
- Last Activity: Outbound
- Email Opened, No Reply
- Email Never Opened
- Meeting Scheduled
- Meeting Completed

Only include an option when the required data already exists reliably in the current database.

If SMS, email-open, meeting-state, or another data source is not currently reliable, do not invent it or build a major subsystem. Clearly report it as deferred.

For email-open filtering:

- Exclude opens caused by VoltSafe employees.
- Exclude internal `@voltsafe.com` opens.
- Use existing tracking data only.

## 4. Sorting

Add these options to the existing sort dropdown:

- Most Recent Activity
- Oldest Activity
- Most Recent Inbound
- Most Recent Outbound
- Most Recent Waiting
- Oldest Waiting
- Longest Waiting on VoltSafe

Clarification:

- `Most Recent Waiting` means the most recently created Waiting for Lead state appears first.
- `Oldest Waiting` means the lead VoltSafe has been waiting on the longest appears first.
- When `Waiting for Lead` is selected and no manual sort has been chosen, default to `Most Recent Waiting`.

Only add sorting options supported by existing data.

All sorting must be server-side and work with pagination.

## 5. Active Filter Display

Use the existing filter-chip or filter-summary pattern if one already exists.

When an Activity Status or Communication filter is active:

- Make the selected value visible in the dropdown.
- Allow the filter to be cleared.
- Ensure `Reset Filters` restores the correct defaults.
- The default Activity Status value must be `All Active Statuses`.

Do not build a new filter-chip framework solely for this task.

## 6. Saved Views and URL State

Use the existing saved-view and URL-query infrastructure.

Ensure the new filters and sorting are preserved when:

- Saving a view
- Reloading the page
- Sharing or revisiting a filtered URL
- Switching pages through pagination

Saved views must distinguish between:

- All Active Statuses
- Never Contacted
- Waiting for Lead
- Any other selected activity status

Do not redesign saved views.

## 7. Shared Implementation

Avoid three separate implementations.

Create or reuse shared definitions and query helpers for:

- Activity Status options
- Communication options
- Date thresholds
- Last inbound activity
- Last outbound activity
- Waiting timestamp
- Last activity type

The Leads, Accounts, and Contacts pages should consume the same shared logic where practical.

Do not create a large new Communication Intelligence platform for this phase.

---

## 8. Database and Performance Constraints

Prefer existing columns, tables, indexes, views, and communication-summary fields.

Do not add a database migration unless it is genuinely required.

If a migration appears necessary:

1. Stop before creating it.
2. Explain exactly why existing data cannot support the feature.
3. Propose the smallest possible migration.
4. Wait for approval.

Requirements:

- No N+1 queries
- Server-side filters
- Server-side sorting
- Existing pagination preserved
- Reasonable performance with approximately 10,000+ CRM records and millions of communication records

Do not perform expensive per-row correlated subqueries if an existing aggregate, lateral join, summary table, or indexed query can be reused.

---

## 9. Permissions and Data Visibility

Filters must respect existing CRM and communication permissions.

A user must not be able to reveal restricted records or communications through:

- Counts
- Filter results
- Sorting
- Saved views
- URL parameters
- Exports

## Definition of Done

This phase is complete when a user can open Leads, Accounts, or Contacts and quickly answer:

- Who did we contact recently?
- Who are we waiting on?
- Who is waiting on us?
- Who has not replied?
- Who has gone dormant?
- Who has never been contacted?
- What was the last communication type?
- Which newly waiting records need attention?
- Which records have been waiting the longest?

Keep the implementation intentionally small, reusable, and production-safe.

Do not add Relationship Health Score, AI classification, engagement scoring, dashboard widgets, advanced nested filter builders, or new background processing in this phase.
