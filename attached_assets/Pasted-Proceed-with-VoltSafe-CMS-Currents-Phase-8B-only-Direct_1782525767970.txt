Proceed with VoltSafe CMS Currents Phase 8B only: Direct Message Attachments.

Do not add group DMs, Guest Currents, external collaborators, slash commands, workflow automation, channel management, notification preferences, typing indicators, or unrelated CRM/task features.

Goal

Allow users to attach files/images to one-to-one Direct Messages in Currents.

Phase 8A added secure one-to-one DMs. Existing Currents already supports attachments for channel and record messages via current_message. Phase 8B should reuse that system for DM messages.

Scope

Add only:

1. File picker / paperclip in DM composer
2. Pending attachment chips before send
3. Upload attachments after sending DM message
4. Display attachments on DM messages
5. Attachment failure handling
6. Safe backend support if needed

Keep scope tight: DM attachments only.

Existing systems to audit first

Before coding, inspect:

* Existing channel Currents attachment upload flow
* Existing record Currents attachment upload flow
* uploadCurrentAttachments()
* CurrentAttachmentChips
* PendingFileChips
* /api/attachments route
* attachment object type support for current_message
* attachment display for MessageRow
* current DM send mutation and message response shape
* DM message GET route payload

Reuse existing components/helpers if possible.

Backend requirements

Prefer no new upload route.

Use the existing /api/attachments route if it already supports:

* objectType = "current_message"
* objectId = DM_MESSAGE_ID

DM messages are still rows in current_messages, so attachment linking should work if message GET routes include attachments.

DM message GET route

Verify and, if needed, update:

GET /api/current/dms/:conversationId/messages

Each message should include:

{
  "attachments": []
}

Use the same attachment fields as channel/record Currents messages.

Security

Verify:

1. User can only upload attachments to a DM message if they are a member of that DM conversation.
2. User cannot attach files to someone else’s DM message by guessing message ID.
3. User cannot view attachments for a DM they are not a member of.
4. Existing attachment download/view permissions are respected or documented.
5. Deleted DM message attachments are hidden/redacted consistently.

If existing /api/attachments route cannot enforce DM membership for current_message, add a safe guard.

Frontend requirements

DM composer

Add paperclip button to the DM composer.

Behavior:

* Opens file picker
* Supports multiple files if existing Currents composer does
* Shows pending file chips before send
* Allows removing pending files before send
* Disables send button or shows uploading state while attachments upload
* Allows text + attachments
* Allows attachment-only message if existing channel composer supports that; otherwise keep body required and document

Upload behavior

Recommended flow:

1. User selects files.
2. User clicks Send.
3. DM message is created first.
4. Attachments upload to:
    * objectType: current_message
    * objectId: created message id
5. DM messages query invalidates/refetches.
6. DM list preview updates.

If some uploads fail:

* Message should still exist.
* Show warning toast:
    * Message sent, but 1 attachment failed to upload.
* Failed files should be clearly handled.

DM message display

DM message rows should display attachments using existing:

* CurrentAttachmentChips
* image thumbnails if supported
* file chips if non-image

Display should match channel/record Currents.

UX requirements

* Paperclip button should match existing channel composer styling.
* Pending chips should look consistent.
* Upload failure state should be clear.
* Dark mode must look good.
* Attachments should not crowd small DM messages.
* No weird scroll jump after upload.
