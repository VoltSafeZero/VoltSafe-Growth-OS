Now implement Universal Drilldowns Phase 3 for Operations + Work.

Primary goal:
Any number, summary card, risk badge, workload count, chart segment, table row, status chip, warning, or health indicator in Operations and Work should be clickable and show the granular underlying records.

Product rule:
If the user can see a number, they should be able to click it and see exactly what created that number.

Do not modify unrelated modules.
Do not weaken permissions.
Do not fake data.
Do not return unpaginated giant datasets.
Do not break the existing Marketing/Pipeline/Insights drilldown system.

2. Backend endpoints

Add new backend drilldown endpoints:

GET /api/operations/drilldown
GET /api/work/drilldown

Both must:
- require authentication
- enforce the same permissions as the source pages
- use metric dispatch via switch/whitelist
- reject unknown metrics with 400
- paginate always
- cap page_size, preferably max 100
- support search where practical
- never return large unpaginated datasets
- return only data the user is authorized to see

Suggested response shape:
- title
- description
- total
- filters
- columns
- rows
- pagination
- available_actions optional

Query params:
- metric
- module optional
- status optional
- owner_id optional
- project_id optional
- account_id optional
- contact_id optional
- date_from optional
- date_to optional
- page
- page_size
- search
- sort optional
- extra filters as needed

6. UI wiring

Wire clickable metrics/cards/chips in Operations and Work pages.

Each clickable item should:
- open UniversalDrilldownSheet
- pass endpoint:
  - /api/operations/drilldown
  - /api/work/drilldown
- pass metric
- pass title
- pass description
- pass any segment/status/date filters
- show pointer cursor and hover state
- include keyboard/focus affordance where practical

Zero-count cards:
- should open useful empty states where practical
- example: “No overdue tasks. Nice. The machine is not on fire.”

Do not make the UI noisy.
Make it obvious and useful.

7. Table row behavior

Where pages show tables/lists:
- preserve existing row click behavior
- if a row already opens a detail drawer, do not replace it
- add drilldowns mainly to summary counts, chips, chart segments, and grouped totals
- avoid double-click ambiguity

8. Chart drilldowns

If Operations or Work pages include charts:
- make chart bars/segments/points clickable where practical
- pass segment filters to the drilldown sheet
- preserve existing tooltip behavior

9. Data integrity

The drilldown total should match the visible card count.

If counts are cached or computed differently:
- refresh on drawer open
- show last refreshed timestamp if available
- log mismatch in development
- do not silently show a different number without explanation

10. Permissions

Respect existing permissions.

Examples:
- users should only see their own Work items if the source page is scoped that way
- Operations pages should only show records the user is authorized to see
- Admin-only/private data should not appear in drilldowns
- Capital records must not appear through Work/Operations drilldowns unless the user has Capital access and the source page already permits that; safest default is exclude Capital-specific data

Backend permission checks are required.
Frontend hiding alone is not enough.
