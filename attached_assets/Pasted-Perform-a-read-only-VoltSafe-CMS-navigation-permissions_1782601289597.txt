Perform a read-only VoltSafe CMS navigation + permissions audit.

Do not change any code, routes, components, permissions, labels, files, or sidebar structure. This is discovery only.

Goal

Before reorganizing the VoltSafe CMS sidebar, I need a factual map of what every current navigation item actually is:

* real implemented feature
* thin placeholder
* stub / coming soon
* duplicate / naming drift
* role-specific/admin-only feature

The goal is to reorganize from evidence, not assumptions.

Part 1 — Full nav inventory

Audit every item currently visible in the sidebar across:

* Today
* Work
* Pipeline
* Operations
* Insights
* Channels
* More
* Admin

For every nav item, produce a markdown table with:

1. Current parent group
2. Current label
3. Current route/path
4. Component/page file rendered
5. Real implemented page / thin placeholder / stub / coming soon
6. Primary purpose of the page
7. Whether it shares a route/component with another nav item
8. Duplicate/overlap candidate? yes/no
9. Evidence: file path, route config, component name, or relevant code reference
10. Suggested disposition:

* Keep
* Rename
* Move
* Merge into X
* Gate by role
* Remove
* Needs decision

Do not guess. If ambiguous, mark it as ambiguous.

Part 2 — Duplicate / overlap investigation

For each suspected duplicate pair below, report definitively whether they are:

* SAME underlying route/component — naming drift, safe to merge
* DIFFERENT real features — keep separate
* PARTIAL overlap — needs product decision
* AMBIGUOUS — more clarification needed

Investigate these specifically:

1. Calendar vs Work Calendar

4. Revenue Intelligence vs Rel. Intelligence vs Revenue Hub vs Revenue Ops vs Revenue Simulator

7. Asset Library vs Assets
8. Projects under Work vs Projects under Operations, if both exist
9. Channels as business ecosystem vs CURRENTS channels
10. Reports vs Executive Dashboard vs Company/Growth dashboard surfaces

For each item, provide:

* route/path evidence
* component/page evidence
* whether it is safe to merge/rename/move
* recommended resolution

Part 4 — Permissions audit

Audit the actual current permission system. Separate these three layers clearly.

A. Nav visibility

Answer:

1. Is the sidebar generated from a central config/array?
2. Or is it hardcoded in JSX?
3. Can individual nav items currently be hidden by role?
4. If yes, where is that implemented?
5. If no, what would be required?
6. Are there existing role/permission fields used by the sidebar?
7. Are hidden items only hidden visually, or also protected at route/API level?

B. Route/page access

Answer:

1. Are frontend routes protected by role?
2. Are backend API routes protected by role?
3. If a user manually visits a route they should not see, what happens?
4. Is unauthorized access blocked server-side?
5. Or is the app relying mostly on nav hiding?
6. Which modules have strong route-level protections?
7. Which modules appear weak/unclear?

Important: hiding a nav item is not security. Identify whether server-side enforcement exists.

C. Action permissions

Answer:

1. Is there a central user role field?
2. Is there a permissions table?
3. Are view/edit/delete/export/admin actions gated consistently?
4. Or are permissions implemented per module?
5. Which modules have clear action permissions?
6. Which modules are inconsistent or unclear?
7. Are admin-only actions protected server-side?

5. Gaps that must be fixed before relying on role-based nav
