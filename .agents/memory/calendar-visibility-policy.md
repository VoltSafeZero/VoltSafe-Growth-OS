---
name: Calendar Privacy Visibility Policy
description: Central resolver pattern for calendar privacy (mirrors mailbox visibility_type); where cross-user calendar leaks tend to hide.
---

Calendar privacy mirrors the mailbox `visibility_type` model, extended with `external_calendar`. The rule that matters most: `private_personal` / `external_calendar` calendars must show ONLY busy/free + start/end time to every non-owner — including admin/master_admin/exec — with no role-based bypass. `company_managed` calendars grant elevated roles (master_admin/admin/exec/executive/ceo/cfo) full view-only access to any internal user's events; non-elevated users need an explicit `calendar_team` grant.

**Why:** Admin privilege overriding private-calendar privacy was an explicit non-goal — the resolver checks PRIVATE_TYPES before any role check, by design, so a bug that reorders these checks silently reintroduces the leak.

**How to apply:** Route every calendar-reading code path (REST endpoints, dashboard widgets, cross-user activity feeds, and any AI/voice-assistant context builder that free-text-searches `calendar_events`) through `resolveCalendarVisibility()` / `sanitizeEventForBusyOnly()` in `server/services/calendar-visibility.ts` — never re-implement the role/ownership check inline. `calendar_connections.visibility_type` and `calendar_events.connection_id` are additive raw-SQL columns (not in Drizzle schema.ts), so always query them via `db.execute(sql...)`, never `db.select()`.

Known leak-prone patterns found and fixed in this codebase: (1) an AI-assistant free-text search helper that queried `calendar_events` directly with no owner/visibility filter at all — any user could surface another user's private event details by asking the assistant a matching question; (2) a global cross-user "activity feed" (surfacing notes/emails/meetings/tasks org-wide for any CRM viewer) that selected `ce.title` directly without joining `calendar_connections` to check `visibility_type`; (3) an account-relationship-intelligence timeline widget that joined calendar events to a CRM account and exposed `ce.title` to any teammate with account access, regardless of the event's own privacy type. In all three cases the fix was the same: LEFT JOIN `calendar_connections`, and CASE/sanitize the title down to `'Busy'` when `COALESCE(visibility_type, 'company_managed') IN ('private_personal','external_calendar')` and the viewer isn't `ce.user_id`. Per-user calendar dashboard widgets that already filter `WHERE ce.user_id = ${userId}` (viewing only your own calendar) need no additional check — the leak vector requires a cross-user query.

Also note: per spec, private_personal/external_calendar busy/free visibility is NOT gated by `calendar_team` permission — it's visible (as "Busy", start/end only) to literally everyone, not just people with an explicit grant. Only `company_managed` events without an elevated role require `calendar_team` for view access (returns 404, not 403, to avoid enumeration).
